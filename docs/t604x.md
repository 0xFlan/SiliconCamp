# T604X (M4 Pro / M4 Max) hardware values

There is **no T604X firmware package yet**: `soc-coverage.py` reports six M4
Pro/Max machines with no silicon package. This page records what is known, so
the package can be written from data instead of guesses.

## Source

Apple's M4 Pro/Max device trees were submitted publicly in October 2026 as
"[PATCH v2 00/10] Initial Apple Silicon M4 Pro/Max device trees and dt-bindings"
(Yureka Lilian, linux-arm-kernel). The series adds `t6040.dtsi` (M4 Pro),
`t6041.dtsi` (M4 Max) and per-machine files. The values below are read from
`t6041.dtsi`; none of them are inferred from the M4 base and none are
copied from the T8132 package.

The series covers a *minimal* device set (CPU, timer, AIC, PMGR, UART, NVMe,
SART, PCIe, I2C, PWM, pinctrl, watchdog). USB, display controllers and their
DARTs are **not** in it, so a T604X virtual memory map cannot yet be written the
way the T8132 map was: those windows have to come from a real machine.

`t6040` is described in the series as "a cut down version of t6041". The full
T6041 die is what a static ACPI table would describe; the shipping SKUs are
smaller, which is the core problem for a per-family package (see below).

## CPUs

The full T6041 die, from `t6041.dtsi`:

| Cluster | Cores | MPIDRs | Compatible | L2 |
|---|---|---|---|---|
| `cluster0` | 4 efficiency | `0x0`–`0x3` | `apple,brava-e` | 4 MB |
| `cluster1` | 6 performance | `0x10100`–`0x10105` | `apple,brava-p` | 16 MB |
| `cluster2` | 6 performance | `0x10200`–`0x10205` | `apple,brava-p` | 16 MB |

That is 16 cores in three clusters. Unlike T8132, the performance cores are
split across **two** clusters with different Aff1 values, which is exactly the
case that broke the first version of `check-acpi.py` (it assumed one P cluster).

Shipping SKUs have fewer cores (14-core M4 Max: 4E + 10P; M4 Pro: 4E + 8P or
4E + 10P), so a static MADT written for 16 cores is wrong on every real machine
except the top SKU.

The vGIC addresses are the same as on T8132 because they are chosen by the
hypervisor, not the SoC: distributor `0x5000000000`, redistributors
`0x5100000000`.

## What a T604X package needs before it can exist

1. **Per-SKU core counts.** A static MADT cannot describe 14- and 16-core
   machines at once. Either one platform package per SKU, or table generation
   from the ADT / boot args at runtime. The latter is the only approach that
   scales to "every Apple Silicon Mac".
2. **USB and display windows.** Absent from the public DT series; needed for the
   low-address MMIO mapping and for any installer path.
3. **DRAM base and size.** Same 1 TB alias as T8132 on recent machines, but
   unconfirmed for T604X; `PrePi` patches it from the boot args at runtime, so
   this is a fallback value only.
4. **A machine to validate on.** Nothing here has run on T604X hardware.

Items 1 and 3 are why `scripts/check-acpi.py` refuses to check a platform it has
no validated expectations for: a 16-core static table would fail on a 14-core
machine, and the checker should say so rather than bless it.
